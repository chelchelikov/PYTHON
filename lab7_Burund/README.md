# Лабораторная работа №7. Вариант 5. Гостиница

Система управления номерами и бронированиями: бронирование, заселение,
выселение, расчёт стоимости. Работа выполнена в два этапа.

| Папка | Содержимое |
|-------|------------|
| `v1_problem/hotel_bad.py` | рабочая версия с намеренными нарушениями SOLID |
| `v2_refactored/` | версия после рефакторинга |

## Запуск

```bash
cd v1_problem && python hotel_bad.py
cd v2_refactored && python main.py
cd v2_refactored && python -m unittest discover -s tests -t . -v
```

## Анализ нарушений в версии 1

| № | Проблема | Принцип | Почему это плохо | Исправление в версии 2 |
|---|----------|---------|------------------|------------------------|
| 1 | `HotelManager` хранит данные, бронирует, считает стоимость, рассылает уведомления, строит отчёты, пишет в файл и печатает в консоль | SRP | любое изменение (формат отчёта, способ уведомления) затрагивает один огромный класс | ответственности разнесены: `RoomService`, `BookingService`, `ReportService`, репозитории, `Notifier`, `ConsoleUI` |
| 2 | `calculate_cost` — цепочка `if room_type == ...` | OCP | новый тип номера требует правки сервиса | стоимость считает сам номер (`night_price`), новый тип — новый класс-наследник `Room` |
| 3 | `MaintenanceRoom(Room)` бросает исключение в `book()` | LSP | наследник нельзя подставить вместо базового класса | ремонт — состояние `RoomStatus.MAINTENANCE`, а не подкласс; все наследники `Room` соблюдают контракт |
| 4 | «толстый» интерфейс `IHotelSystem` из 8 методов | ISP | клиент, которому нужен только отчёт, зависит от бронирования, уведомлений и файлов | узкие протоколы `ReadableRepository`, `WritableRepository`, `Notifier`; `ReportService` зависит только от чтения |
| 5 | `self.email_sender = EmailSender()` внутри сервиса | DIP | бизнес-логика жёстко связана с инфраструктурой, её нельзя протестировать без отправки писем | зависимости передаются в конструктор, сборка — в `main.py` |
| 6 | `print()` внутри бизнес-методов | SRP | логику нельзя переиспользовать в вебе/боте и тестировать | `input()`/`print()` есть только в `ui/console.py` |

## Структура версии 2

```
v2_refactored/
├── main.py                      # корень композиции (DI), выбор хранилища и уведомлений
├── models/                      # entities.py, enums.py, exceptions.py
├── interfaces/                  # repository.py (ISP), notifier.py
├── repositories/                # InMemoryRepository, JsonFileRepository, serializers
├── services/                    # RoomService, BookingService, ReportService
├── infrastructure/notifier.py   # ConsoleNotifier, FileNotifier, CompositeNotifier
├── ui/console.py                # ConsoleUI
└── tests/test_services.py       # 8 тестов с FakeNotifier
```

## Применение SOLID

- **SRP** — каждый класс отвечает за одно: хранение, бронирование, отчёты, уведомления, интерфейс.
- **OCP** — новые типы номеров (`StandardRoom`, `SuiteRoom`, `FamilyRoom`) и уведомлений
  добавляются новыми классами; `BookingService` при этом не меняется. Сериализатор
  находит подклассы `Room` автоматически.
- **LSP** — `InMemoryRepository` и `JsonFileRepository` взаимозаменяемы, клиентский код одинаков
  (проверяется тестом `test_json_repository_persists_data`).
- **ISP** — `ReadableRepository` / `WritableRepository` / `Notifier`.
- **DIP** — сервисы получают репозитории и уведомитель через конструктор.

## Сравнение архитектур

| Характеристика | До рефакторинга | После рефакторинга |
|----------------|-----------------|--------------------|
| Ответственность классов | один класс делает всё | один класс — одна ответственность |
| Зависимости | конкретные классы создаются внутри | абстракции, внедрение через конструктор |
| Расширяемость | правка `if/elif` в сервисе | новый класс без изменения сервиса |
| Тестируемость | мешают `print` и e-mail | тесты с `FakeNotifier` и хранилищем в памяти |
| Связность | низкая, всё перемешано | высокая внутри модулей |
| Использование абстракций | один «толстый» интерфейс | узкие `Protocol`, ABC `Room` |
