# Лабораторная работа №13. Вариант 5. Отель — номера

**MongoDB** хранит полные документы номеров (источник истины), **Redis** даёт быстрый
доступ к часто запрашиваемым данным: свободные номера, результаты поиска, кэш карточки номера.

## Запуск

```bash
pip install -r requirements.txt
docker compose up -d          # MongoDB :27017, Redis :6379
python -m app.main            # при пустой коллекции она заполняется 22 номерами
pytest -v                     # 14 тестов
```

Проверка сервисов: `docker compose ps` (статус healthy), `redis-cli ping` → `PONG`,
`mongosh --eval "db.adminCommand('ping')"`. Приложение подключается к `localhost` по
пробрасываемым портам 27017 и 6379 (переменные `MONGO_URL`, `REDIS_URL`).

Если MongoDB или Redis не запущены, приложение сообщает об этом и завершается без трассировки;
тесты в этом случае автоматически используют `mongomock` и `fakeredis`.

## Документ MongoDB

База `hotel`, коллекция `rooms`:

```json
{
  "_id": ObjectId("..."),
  "number": "302",
  "room_type": "suite",
  "floor": 3,
  "price": 8500,
  "state": "free",
  "features": {"area_m2": 42, "beds": 2, "view": "sea", "smoking": false, "balcony": true},
  "amenities": ["wifi", "tv", "minibar", "bathtub"]
}
```

Обязательные поля: `number`, `room_type`, `floor`, `price`, `state`, `features`.
`features` — вложенный документ, `amenities` — массив, `room_type` и `state` — категория и статус.

## Запросы MongoDB (`repository.py`)

| № | Запрос | Метод |
|---|--------|-------|
| 1 | свободные номера: фильтр по `state`, `room_type`, `features.beds`, `price` + сортировка по цене | `free_rooms` |
| 2 | номера типа, сортировка по убыванию цены | `by_type` |
| 3 | диапазон цен `$gte/$lte` | `by_price_range` |
| 4 | по вложенному полю `features.view` | `with_view` |
| 5 | по элементу массива `amenities` | `with_amenity` |
| 6 | содержит все удобства `$all` | `with_all_amenities` |
| 7 | топ-N дорогих (`sort` + `limit`) | `most_expensive` |
| 8 | топ-N по площади (сортировка по вложенному полю + `limit`) | `largest` |
| 9 | агрегация: количество, средняя/минимальная/максимальная цена по типам | `stats_by_type` |
| 10 | агрегация: количество по состояниям | `stats_by_state` |
| 11 | агрегация `$unwind`: популярность удобств | `amenity_popularity` |

## Индексы

| Индекс | Поля | Какие запросы ускоряет |
|--------|------|------------------------|
| `uniq_number` | `number` (unique) | поиск по номеру комнаты; заодно запрещает дубликаты |
| `state_type_price` | `state, room_type, price` | поиск свободных номеров нужного типа с сортировкой по цене — главный запрос приложения. Равенство по `state` и `room_type` идёт первым, `price` последним, поэтому сортировка берётся прямо из индекса |
| `amenities` | `amenities` (multikey) | поиск по элементу массива |

План запроса `{state: "free", room_type: "suite"}` с сортировкой по цене:
`FETCH <- IXSCAN(state_type_price)` — используется индекс, без полного просмотра коллекции
(`COLLSCAN`) и без отдельной сортировки в памяти.

## Redis

| Тип | Ключ | Задача |
|-----|------|--------|
| String + TTL | `room:{id}` (120 с) | кэш карточки номера (cache-aside) |
| String + TTL | `search:free:{тип}:{кроватей}:{цена}` (60 с) | кэш результатов поиска свободных номеров |
| Set | `rooms:free` | id свободных номеров, проверка `SISMEMBER` за O(1) |
| Sorted Set | `rooms:popular` | рейтинг просмотров номеров (`ZINCRBY`, `ZREVRANGE`) |
| List | `searches:recent` | 10 последних поисковых запросов (`LPUSH` + `LTRIM`) |
| Hash | `cache:stats` | счётчики попаданий и промахов (`HINCRBY`, `HGETALL`) |

Операции: `SET … EX`, `GET`, `DEL`, `EXISTS`, `TTL`, `SCAN`, `SADD`, `SREM`, `SISMEMBER`, `SCARD`,
`ZINCRBY`, `ZREVRANGE`, `LPUSH`, `LTRIM`, `LRANGE`, `HINCRBY`, `HGETALL`.

### Cache-aside и инвалидация

Сценарий из теста `test_cache_aside_and_invalidation` и меню (пункты 2 → 2 → 5 → 2):

1. `GET room:{id}` в Redis — промах, документ читается из MongoDB (`Источник: MONGODB`);
2. документ записывается в Redis с TTL 120 с;
3. повторный запрос обслуживается из Redis (`Источник: REDIS`);
4. номер изменяется в MongoDB;
5. `DEL room:{id}` и всех `search:*`, обновление множества `rooms:free`;
6. следующий запрос снова идёт в MongoDB;
7. обновлённые данные кладутся в Redis.

## Производительность

Чтение одного документа по `_id` (MongoDB 7 в Docker, Redis 7, локально):

| Количество запросов | MongoDB, всего | Redis, всего | MongoDB, мс/запрос | Redis, мс/запрос |
|--------------------:|---------------:|-------------:|-------------------:|-----------------:|
| 100 | 0.058 с | 0.013 с | 0.584 | 0.134 |
| 1 000 | 0.518 с | 0.109 с | 0.518 | 0.109 |
| 10 000 | 5.223 с | 1.100 с | 0.522 | 0.110 |

Redis примерно в 5 раз быстрее: данные лежат в оперативной памяти, а `GET` по ключу — самая
простая операция без разбора запроса, планировщика и выбора индекса. Сериализация JSON в
Python занимает заметную часть времени Redis. Обе базы работают локально, поэтому сетевая
задержка мала; при удалённой MongoDB разница была бы больше. Среднее время почти не зависит
от числа запросов, значит производительность стабильна. Это не значит, что Redis «лучше»:
MongoDB умеет сложные запросы, агрегации и надёжно хранит данные на диске, а Redis хорош как
быстрый слой поверх неё.
