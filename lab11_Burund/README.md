# Лабораторная работа №11. Вариант 5. Отель

REST API из лабораторной №10 переведено на реляционную БД (**SQLite**, чистый SQL без ORM),
добавлены кэш **Redis** (поиск свободных номеров, карточка номера) и локальная имитация
**CDN** для фотографий номеров.

| Часть | Что сделано |
|-------|-------------|
| SQL | `db/schema.sql` (8 таблиц, PK/FK/UNIQUE/CHECK, 4 индекса), `db/seed.sql`, `db/queries.sql` (20 запросов) |
| Python | `repository.py` (весь SQL, параметризованные запросы), `service.py`, `routes.py`, `app.py` |
| Транзакция | бронирование нескольких номеров: `BookingRepository.create` (`BEGIN IMMEDIATE … COMMIT / ROLLBACK`) |
| NoSQL | Redis: cache-aside с TTL, счётчик просмотров (`INCR`), `nosql/redis_demo.py` |
| CDN | `cdn/origin_server.py` (origin), `cdn/edge_server.py` (edge с кэшем), `cdn/check_cdn.py` (замеры) |

## Запуск

```bash
pip install -r requirements.txt
redis-server &                  # без Redis приложение работает с кэшем в памяти
python app.py                   # REST API http://127.0.0.1:5000 (hotel.db создаётся автоматически)
python client.py                # консольный клиент
python run_queries.py           # выполнить все SQL-запросы из db/queries.sql
python nosql/redis_demo.py      # операции Redis и сравнение с SQL

cd cdn
python origin_server.py &       # origin  http://127.0.0.1:8080/static/
python edge_server.py &         # CDN     http://127.0.0.1:8081/static/
python check_cdn.py             # сравнение origin и CDN

pytest -v                       # 17 тестов
```

## Схема БД

```
room_types 1───N rooms 1───N room_photos
                  │ N
                  │            amenities
                  ├──── N:M ──── (room_amenities)
                  │ N
              booking_rooms  (N:M rooms ↔ bookings)
                  │ N
guests 1───N bookings 1──┘
```

- **1:N**: `room_types → rooms`, `rooms → room_photos`, `guests → bookings`.
- **N:M**: `rooms ↔ amenities` через `room_amenities`, `rooms ↔ bookings` через `booking_rooms`
  (одна бронь может включать несколько номеров).
- Внешние ключи: `rooms.type_id`, `room_photos.room_id`, `room_amenities.*`, `bookings.guest_id`,
  `booking_rooms.*`.
- Данные: 12 номеров, 4 типа, 7 удобств, 5 гостей, 6 бронирований.

## Индексы

| Индекс | Для какого запроса |
|--------|--------------------|
| `idx_rooms_status_capacity (status, capacity)` | поиск свободных номеров по вместимости (`/rooms/available`), см. запрос 20 с `EXPLAIN QUERY PLAN` |
| `idx_rooms_type (type_id)` | фильтр `room_type` и `JOIN rooms ↔ room_types` |
| `idx_bookings_guest (guest_id)` | история бронирований гостя |
| `idx_booking_rooms_room (room_id)` | проверка пересечения периодов бронирования номера |

Индекс ускоряет поиск, но занимает место и замедляет каждую вставку и изменение
(индекс тоже нужно обновлять). Поэтому индексы создаются только под реальные частые
запросы, а не на каждом столбце.

## SQL injection

Если подставлять значения в SQL строкой (`f"... WHERE name = '{name}'"`), строка
`' OR '1'='1` превращает условие в «всегда истинно», и злоумышленник меняет смысл запроса.
В `repository.py` все значения передаются параметрами (`?`): драйвер передаёт их отдельно от
текста запроса, и они никогда не исполняются как SQL. В текст запроса попадают только
имена столбцов из белого списка (`SORT_COLUMNS`). Тест `test_filters_and_sql_injection`
показывает, что `' OR '1'='1` в фильтре просто ничего не находит.

## Транзакция

`POST /bookings` бронирует сразу несколько номеров:

1. найти или добавить гостя;
2. создать запись `bookings`;
3. для каждого номера проверить, что он существует, не на обслуживании, вмещает гостей
   и свободен на эти даты, затем добавить строку `booking_rooms`;
4. записать итоговую стоимость.

Если хотя бы один номер недоступен, выполняется `ROLLBACK`: не остаётся ни гостя, ни брони,
ни части номеров (тест `test_booking_transaction_rollback`). Если всё успешно — `COMMIT`.

## API

Все endpoints лабораторной №10 (`GET/POST /rooms`, `GET/PUT/PATCH/DELETE /rooms/{id}`,
`/rooms/available`, `/rooms/statistics`) работают через SQL, плюс:

| Метод | Endpoint | Назначение | Код |
|-------|----------|------------|-----|
| GET | `/rooms/available?check_in=&check_out=&guests=&amenity=` | свободные номера на период (кэш Redis) | 200 |
| POST | `/bookings` | бронирование (транзакция) | 201 |
| GET | `/bookings/{id}` | бронирование | 200 |
| POST | `/bookings/{id}/cancel` | отмена | 200 |

Ответы `/rooms/{id}` и `/rooms/available` содержат заголовок `X-Data-Source: db | cache`.
В карточке номера поле `photos` содержит ссылки на CDN.

## Redis

Выбран **Redis**, потому что в варианте кэшируются результаты поиска свободных номеров:
это короткоживущие данные «ключ → значение», которые нужно отдавать быстро, а
источником истины остаётся SQL.

- **cache-aside**: `GET /rooms/7` → ключ `hotel:room:7` в Redis → если нет, SELECT → SET с TTL;
- поиск: ключ `hotel:search:available:<хэш параметров>`;
- **TTL = 60 с**: изменяемые данные нельзя кэшировать бесконечно, иначе пользователь увидит
  устаревшие цены и занятые номера как свободные;
- **cache invalidation**: при изменении номера удаляется `room:{id}` и все `search:*`, при
  бронировании и отмене — все `search:*`;
- `INCR hotel:views:room:{id}` — счётчик просмотров номера;
- `nosql/redis_demo.py`: SET, GET, EXPIRE/TTL, INCR, DELETE и поиск свободных номеров
  целиком на структурах Redis (HSET, ZADD, SADD, ZRANGEBYSCORE) с проверкой, что результат
  совпадает с SQL.

Сравнение: SQL-запрос гибче (любые фильтры, JOIN, транзакции), а в Redis под каждый
вид поиска приходится заранее строить структуры и вручную поддерживать их актуальность.
Поэтому Redis используется как кэш, а не как основная БД.

## CDN

Реальный CDN недоступен, поэтому используется разрешённая локальная имитация:

- `origin_server.py` — исходный сервер, задержка 150 мс («далеко»), `Cache-Control: no-cache`;
- `edge_server.py` — edge-сервер: при первом запросе забирает ресурс с origin (`X-Cache: MISS`),
  затем отдаёт из своего кэша (`X-Cache: HIT`, заголовок `Age`), выставляет
  `Cache-Control: public, max-age=86400` для картинок и `3600` для CSS/JS.

Ресурсы: `static/images/standard.png`, `deluxe.png`, `suite.png`, `css/style.css`, `js/app.js`,
`index.html`.

Результаты `check_cdn.py`:

| Ресурс | Origin, 1-й / 2-й запрос | CDN, 1-й запрос (MISS) | CDN, 2-й запрос (HIT) |
|--------|--------------------------|------------------------|-----------------------|
| `images/standard.png` (1257 Б) | 157 / 153 мс | 182 мс | 2 мс |
| `images/deluxe.png` (1281 Б) | 153 / 153 мс | 154 мс | 2 мс |

Первый запрос через CDN не быстрее origin (edge сам идёт на origin), зато все следующие
пользователи получают ресурс из ближайшего edge почти мгновенно, а origin не нагружается.

## Сравнение технологий

| Характеристика | PostgreSQL / SQLite | MongoDB | Redis | CDN |
|----------------|---------------------|---------|-------|-----|
| Назначение | основное хранилище | документы с гибкой схемой | кэш, счётчики, сессии | доставка статики |
| Структура | таблицы, связи | JSON-документы | ключ → значение, хэши, множества | файлы по URL |
| Хранение | диск | диск | оперативная память | кэш edge-серверов |
| Запросы | SQL, JOIN, агрегаты | find, aggregation | по ключу | HTTP GET |
| Транзакции | ACID | ограниченные | MULTI/EXEC, без отката | нет |
| Кэширование | нет (источник истины) | нет | да, TTL | да, Cache-Control |
| Масштабирование | вертикальное, реплики | шардирование | кластер | географическое |
| Типичные данные | номера, гости, брони | каталоги, логи | результаты поиска, просмотры | фото, CSS, JS |
| Когда использовать | важна целостность | меняющаяся структура | нужна скорость | много публичных файлов |

**Почему данные хранятся именно здесь:**
номера, гости и брони → SQL (связи, транзакции, нельзя потерять);
результаты поиска свободных номеров и счётчики просмотров → Redis (быстро, можно
пересчитать, устаревают за минуту);
фотографии номеров → CDN (большие, одинаковые для всех, редко меняются; в БД — только путь).
